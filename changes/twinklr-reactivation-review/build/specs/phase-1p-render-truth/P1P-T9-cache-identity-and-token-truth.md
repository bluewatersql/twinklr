# P1P-T9 — Cache identity + token truth

Phase: 1P (Render Truth) · Lane: I (instrumentation/cache, parallel) · Executor: opus · Verifier: opus · Depends on: P0-T4

## Objective

Make cache reuse real and cost telemetry trustworthy — in one change, because the pieces
are interlocked. Today every run writes to a private, permanently-unreachable cache
subtree (random session UUID + CWD-relative root), so no LLM work is ever reused; and the
moment reuse *does* work, any prompt edit silently serves plans generated by the old
prompt, because prompt content is in no cache key. Separately, per-stage token figures are
already wrong on the only shipped path.

**Deterministic session-ID + cache-root anchoring + prompt-content hashing land together.
This is a hard constraint (see "Sequencing constraints").** Per-call token attribution
is bundled here because it is the other half of "instrumentation you can believe".

### 2. The cache root is CWD-relative (P1-M3, MEDIUM, verifier-added). Verbatim:

> `CacheConfig.cache_path` defaults to the relative `"data/cache/agent"`
> (`config/models.py:126`), and `absolute_path` (`io/models.py:16-25`) calls
> `Path(path).resolve()` **before** testing `is_absolute()` — so the guard can never fire and
> the relative path is silently anchored to the process CWD. `session.py:152-156` passes it

## Current behavior

- Every `twinklr run` invents a fresh `session_id` UUID, so its cache entries are written
  into a subtree no later run can address. Nothing ever evicts them.
- The cache root resolves against the process CWD, so the same job run from two
  directories uses two caches, silently.
- Prompt-pack content is absent from every cache key; the only invalidation lever is a
  hand-edited `cache_version` literal.
- Per-stage token metrics are computed as deltas of a shared cumulative counter across
  `await` boundaries, while `profile` and `lyrics` run concurrently in one wave — so every
  shipped run's per-stage token figures are systematically over-counted.
- The correct per-call figure exists on `LLMResponse.metadata.token_usage` and is thrown
  away by the repair loop.

## Target behavior

1. **Deterministic session identity.** The CLI supplies a `session_id` derived from job
   inputs (audio-file content hash + config fingerprint), so an identical re-run addresses
   the same cache subtree. A user-supplied override remains possible.
2. **Anchored cache root.** Cache paths resolve against a configured project root, not the
   CWD. `absolute_path` either rejects relative input or is renamed to say it resolves.
3. **Prompt content in the key.** Every LLM stage's cache key includes a hash of the
   prompt-pack content it will render, so editing a prompt invalidates the affected
   entries automatically. The hand-maintained `cache_version` literal remains as a manual
   escape hatch but is no longer the only lever.
4. **Per-call token attribution.** `LLMResponse`'s `token_usage` is threaded out of
   `_execute_with_repair_async` (summed across repair attempts) into `AgentResult` and the
   completion log, replacing the shared-counter delta. Per-stage metrics are correct even
   when two stages run concurrently.

**Non-goals.** No cache **eviction** implementation (P1-F4's "add eviction" half is
explicitly deferred — record it as a follow-up). No `compute_fingerprint` revival (it is
dead; keys are built in `execute_step`). No model retarget (P2P-T10). No fix for the
wave-failure sibling discard (P1-M1). Do not separate reasoning tokens from
`output_tokens` unless the provider exposes them directly — record the gap for the
retarget task, which is where it becomes material.

- `packages/twinklr/core/session.py` — `session_id` default (`:69`), the documented
  capability (`:59-60`, `:121`), cache construction (`:152-156`), provider construction
  (`:173-178`).
- `packages/twinklr/core/config/models.py` — `CacheConfig.cache_path` (`:126`), project-root
  configuration.
- `packages/twinklr/core/io/models.py` — `absolute_path` (`:16-25`).
- `packages/twinklr/core/pipeline/execution.py` — key assembly (`:113-119`), the
  `f"{stage_name}_tokens"` metric (`:189`).
- Each LLM stage's `cache_key_fn` / `get_cache_key` (profile, lyrics, macro, moving-heads,
  group) — add the prompt hash.
- `packages/twinklr/core/agents/async_runner.py` — the delta snapshots (`:86`, `:120`),
  `_execute_with_repair_async` (`:313`) return shape, and `_safe_log_complete`.
- `packages/twinklr/core/agents/providers/openai.py` — `LLMResponse.metadata.token_usage`
  population is the source of truth; no change expected beyond verifying it.

Design decisions already made (do not relitigate):
- **Session ID is derived, not removed from the key.** The review offers "derive … or drop
  it from the key entirely"; derivation preserves the deliberate, documented capability and
  keeps runs isolable when a user wants that.
- **The prompt hash covers rendered prompt-pack *content***, not `pack.yaml`'s
  `pack_version` — the addendum states that field is "inert and inverted — the signal must
  be built, not read".
- **Token usage comes from the response, not from a counter diff.** Delete the
  snapshot-and-subtract path rather than guarding it with a lock; the counter is already
  lock-protected and that is not the problem.
- **All four items land as one change.** Landing the session-ID fix alone makes the
  stale-prompt hazard live the same day; landing the cache-root fix separately makes the
  session-ID fix look broken.

## Acceptance criteria

- [ ] Two identical `twinklr run` invocations (same audio, same config) produce the **same**
      `session_id` and the second run's LLM stages report cache **hits**. Tested with a
      fake provider — no live API call.
- [ ] Changing the audio file or the config changes the `session_id`.
- [ ] Running from two different working directories with the same configured project root
      addresses the **same** cache tree. A test asserts the resolved cache root is
      CWD-independent.
- [ ] `absolute_path` no longer resolves-then-checks; relative input is either rejected or
      the function is renamed and its callers updated. `grep` shows no
      `Path(path).resolve()` preceding an `is_absolute()` test.
- [ ] Editing prompt-pack content changes the cache key for the affected stage(s) and only
      those stages. A test mutates a prompt fixture and asserts a key change; a control
      test asserts an unrelated stage's key is unchanged.
- [ ] The model ID remains in every LLM stage key (do not regress the one thing that was
      already right — the addendum's "M1 retarget SAFE" verdict must survive).
- [ ] Per-stage token metrics are exact under concurrency: a test runs two stages
      concurrently against a fake provider with known per-call usage and asserts each
      stage's reported tokens equal its own calls' sum (today: over-counted).
- [ ] Repair attempts are summed: a call that repairs twice reports the total across all
      three requests.
- [ ] `async_runner.py` contains no `get_token_usage()` delta arithmetic for per-call
      attribution.
- [ ] New cache tests live in `tests/unit/caching/` and cover at least: key stability
      across runs, TTL expiry, meta/key mismatch, corrupted-artifact-to-miss — the failure
      modes P1-F29 lists as unexercised.
- [ ] `make validate` check-only equivalents pass.

## Effort & risk

**Effort: M–L.** Four coupled changes across the session, cache, key-assembly, and runner
layers.

**Main risk: turning cache reuse on for the first time.** Every prior run's entries are
unreachable (random UUIDs), so the first deterministic run is a clean miss — good. But from
then on, a stale entry is *possible* for the first time in this codebase's history, and
every remaining un-keyed input (temperature is in profile/lyrics keys but not planner keys;
`min_pass_score` is in planner keys yet behaviorally inert) becomes a potential staleness
or experiment-confounding source. Mitigation: the prompt hash lands in the same change (the
constraint); audit each stage's `cache_key_fn` for un-keyed inputs while you are in there
and record any remaining gaps in the handoff for P2P's experiment work.

**Second risk: the derived `session_id` hashes something unstable** (an absolute path, a
timestamp, a dict with nondeterministic ordering), making reuse silently fail again.
Mitigation: hash audio **content**, not its path; sort config keys; assert stability across
two processes, not just two calls in one process.

**Third risk: threading `LLMResponse` out of the repair loop touches every agent call
site.** Mitigation: keep the return-type change additive (return the response alongside
the content) rather than reshaping every caller, and let mypy find the sites.
